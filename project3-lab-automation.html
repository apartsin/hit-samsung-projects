Self-Driving Camera Lab

Software that remotely controls a camera test lab (lights, motorized stages, focus motors and the camera under test), finds the best setup on its own, and searches the space of test conditions for the cases where the camera performs worst.

A research project for an industry customer. There is no ready recipe: the team defines the details of the method, reads the literature, tries ideas, measures, and learns from what does not work. The project requires independent work, proactive exploration and a lot of trial and error, with regular reporting to the supervisor and the Samsung mentor.

On-site visits required: the equipment is in a test lab on site. Most development is done remotely against simulated (mock) devices, but integration and testing with the real hardware require regular visits to the lab. Students should plan for scheduled lab days during both semesters, with more of them in the integration phase.

Description

Camera image quality is measured in labs with test charts, calibrated lights and precise positioning. Today, much of this setup is manual: moving the camera, aligning it to the chart, setting the light, focusing, and capturing. This project turns the lab into a programmable, self-driving system in three steps.

(a) Unified API. One software interface for every device in the lab: light sources (intensity, color temperature, flicker), motorized positioning (linear and rotation stages, pan-tilt, robot arm), focus motors, and the camera or phone under test. Every capture is logged together with the full state of all devices.

(b) Automatic best setup. Algorithms that find the right settings on their own: align the camera to the chart (position and angle), make the lighting uniform, and find the best focus.

(c) Smart exploration and failure hunting. A strategy that scans the space of configurations with as few captures as possible, first to get a representative sample of camera behavior, then to actively hunt for configurations where the camera under-performs. Both static conditions and dynamic ones (moving targets, camera shake, changing or flickering light) are covered.

Tasks to automate

The lab team has defined the first tasks. Each action must be fitted to the specific chart being shot, so every chart gets a definition (its markers, regions of interest and target pose) that the routines read.

Main challenges

  • Computer vision on RAW CFA data. The sensor delivers a RAW Bayer mosaic, not a finished color image. Marker detection, focus and exposure measurements have to work directly on this data: subtract the black level, split the mosaic into its color planes (or use the green plane at half resolution), and measure there, without running a full camera pipeline.
  • Controlling hardware through multiple APIs. Motion stages, lights, power switches and the sensor capture software all come with different interfaces. The project wraps them in one consistent API.

Motivation

  • Speed and repeatability. Automated setups run day and night and repeat a test exactly, which a manual setup cannot.
  • Better test coverage. The number of combinations of light, distance, angle, motion and camera settings is huge. A grid search is far too slow; smart sampling covers the space with a fraction of the captures.
  • Finding weak spots early. Actively searching for the conditions where image quality drops finds problems before users do, and points engineers to what to fix.
  • Data for other projects. The lab produces labeled test data for models such as the patch quality scanner (Project 1) and the RAW sensor twin (Project 2).

Goals and deliverables

  1. A device layer with a common interface (connect, set, read, move, capture), drivers for each lab device, and a mock version of each device for development without hardware.
  2. A lab service: a documented REST or gRPC API, an event bus for device status, and a database of every capture with its full configuration.
  3. Auto-setup routines: chart alignment with fiducial markers, autofocus search, and lighting uniformity optimization.
  4. An exploration engine: space-filling sampling, Bayesian optimization, and failure search, with a report that maps where the camera performs well and badly.
  5. Dynamic tests: synchronized runs with motion and changing light.
  6. A demonstration in the lab showing a full unattended test campaign.

Suggested approach

  • Learn from Android Camera ITS. Google's Camera Image Test Suite already drives phones over ADB with Python, shows charts on a tablet, rotates phones with an Arduino-controlled rig, and has an automated "ITS-in-a-box" setup. It is a good template for the API and test flow.
  • Hardware abstraction. Follow the device model of Bluesky and ophyd (or ophyd-async): every device exposes readable and settable signals, and a run engine records every step.
  • Simulate first. Build a simple simulator of the rig (render a chart under a given pose, light and focus) so that the search algorithms can be developed and tested before the lab visits.
  • Measure image quality. Use slanted-edge sharpness (MTF Mapper), noise, distortion and color metrics as the scores the search optimizes.
  • Search in stages: Sobol or Latin hypercube sampling for coverage; Bayesian optimization (BoTorch / Ax) for best settings; level-set estimation to map the boundary between good and bad quality; quality-diversity search (MAP-Elites with pyribs) to collect many different failure cases.

What students will need

A map of the concepts, methods and tools this project touches. The first weeks are for learning the essentials.

Concepts

  • Camera image quality metrics: sharpness (SFR / MTF), noise, distortion, color accuracy, flare
  • RAW sensor data: Bayer CFA, black level, color planes, clipping
  • Exposure, gain and white balance
  • Camera calibration, camera pose, homography
  • Light: color temperature, illuminance, PWM flicker
  • Motion control: stepper and servo motors, stages, kinematics
  • Rolling shutter, motion blur, image stabilization
  • Design of experiments, search spaces

Algorithms and techniques

  • Fiducial markers (ArUco, ChArUco, AprilTag) and pose estimation (PnP)
  • Visual servoing for alignment
  • Computer vision directly on RAW CFA frames
  • Auto exposure from histograms; gray-world and gray-patch white balance
  • Autofocus: focus measures, hill climbing, golden-section search
  • Quasi-random sampling: Sobol, Latin hypercube
  • Gaussian processes and Bayesian optimization
  • Active learning, level-set estimation
  • Falsification and adversarial testing, quality-diversity (MAP-Elites)

Software engineering

  • Hardware abstraction layers, device drivers
  • REST and RPC API design, OpenAPI
  • Asynchronous programming, event buses
  • Mock devices and automated testing
  • Logging, data provenance, experiment databases

Evaluation

  • Alignment repeatability (reprojection error, angle)
  • Autofocus accuracy and number of steps
  • Share of a campaign run unattended
  • Coverage vs. number of captures
  • Failures found per capture budget vs. random sampling

Tools and frameworks

  • Python, asyncio, FastAPI or gRPC, MQTT or ZeroMQ
  • Bluesky, ophyd-async, PyVISA, PyMeasure
  • ADB, Camera2, scrcpy, gphoto2, Harvester (GenICam)
  • Zaber Motion Library (the lab's stages); other SDKs: Thorlabs Kinesis, PI pipython
  • DMX lighting control (USB-DMX, OLA); web power switch API
  • rawpy, NumPy for RAW frames
  • Arduino, GRBL for low-cost motion; ROS 2 and MoveIt 2 for robot arms
  • OpenCV, MTF Mapper
  • SciPy (qmc), BoTorch, Ax, Optuna, pyribs, VerifAI
